## 0. 먼저 — 감사 문서의 추정 하나가 틀렸다

감사 F2에 "존이 5분봉이 아니라 상위 시간대에서 오는 것일 수 있다"고 적었다. **틀렸다.** 원문 §10이 의사코드로 직접 답한다:

```python
def build_zones(bars_5m, lookback_days=None):
    if lookback_days is None:
        lookback_days = 3 if at_all_time_high(bars_5m) else 10
```

세 가지가 이 한 조각으로 확정된다:

| 쟁점 | 원문의 답 |
|---|---|
| 존의 입력 시간대 | **5분봉이 맞다** (`bars_5m`) |
| 10일 / 3일 요구 | **원문 그대로다.** 구현의 발명이 아니다 |
| `at_all_time_high` | **같은 5분봉에서 계산한다.** 외부 입력이 아니다 |

따라서 F2는 "요구가 잘못됐다"가 아니라 **"요구는 맞는데 데이터를 그만큼 안 가져온다"**이고, F3은 "생산자를 새로 만들어야 한다"가 아니라 **"이미 있는 봉에서 계산하면 된다"**이다. 둘 다 원래 추정보다 **작고 명확한 수정**이 된다.

이 정정에 따라 감사 문서 F2의 "추가 의심" 항목은 폐기한다.

## 1. 수정 순서와 이유

```
1. F2+F3  존 창 확장 + ATH 계산      ← 이걸 하기 전에는 아무것도 관측되지 않는다
2. F8     존 관측점을 스윙으로 교정   ← F2와 같은 파일, 같은 검증 실행
3. F1     양방향 평가                ← F2 이후라야 효과가 보인다
4. F5     정책 수치                   ← 코드 아님, 운영자 결정
5. F6     보유 포지션 청산 규칙       ← 페이퍼 승격 전까지
```

**순서가 중요한 이유:** 현재 모든 결정이 `NO_MARKED_ZONE` 때문에 REJECT로 고정되어 있다. F1을 먼저 고쳐 숏 평가를 켜도 **결과는 여전히 전부 REJECT이고, 고쳐졌는지 확인할 방법이 없다.** F2가 관측 가능성 자체를 되돌려준다.

## 2. F2 — 존 창을 원문이 요구하는 길이로

### 원인 (확정)

`binance_usdm.py:16` `_REST_LIMIT = 1500`, 그리고 `completed_bars`가 klines를 **한 번만** 호출한다.

```python
rows = await self._rest.klines(
    symbol=_SYMBOL, interval=interval,
    end_time_ms=_epoch_ms(end_at), limit=_REST_LIMIT,
)
```

5분봉 1,500개 = 5.2일 = 날짜 7개. `zones.py:100`이 요구하는 10개에 미달 → `zones = ()`.

**1,500은 Binance의 한계가 맞지만 요청당 한계다.** `/fapi/v1/klines`는 `endTime`을 받으므로 역방향 페이징이 가능하다. 현재 코드는 페이징을 하지 않는다.

### 수정

`completed_bars`가 요청한 길이를 채울 때까지 `endTime`을 뒤로 밀며 반복한다.

```
필요량: 10일 × 288개/일 = 2,880개  →  요청 2회
```

설계상 정해야 할 것:

- **얼마나 가져올지 누가 정하는가.** 존은 10일을 원하고, MACD 워밍업은 그보다 훨씬 적게 원하며, 회귀(SMA 200)는 200개면 된다. 소비자마다 다른 길이를 요구하므로 `completed_bars(timeframe, end_at, *, minimum_days=...)` 형태로 **호출자가 말하게** 하는 편이 낫다. 기본값을 두면 F3과 같은 결함이 다시 생긴다 — 아무도 지정하지 않는 숫자가 결과를 정하는 상태.
- **연속성 검증을 페이지 경계에서 유지한다.** `_compile_klines`가 5분 간격 연속성을 요구하고, `zones.py:96`도 독립적으로 재검사한다. 페이지를 이어 붙일 때 경계에서 한 봉이 중복되거나 빠지면 `ZONES_EVIDENCE_INVALID`로 조용히 바뀐다 — 지금의 `NO_MARKED_ZONE`과 증상이 다를 뿐 결과는 같다.
- **거래소가 그만큼 없을 때.** 신규 상장이나 데이터 공백이면 10일이 안 나온다. 그때는 **짧은 창으로 존을 만들지 말고** 지금처럼 빈 존을 반환해야 한다. 3일치로 10일 규칙을 흉내 내는 것은 증거 날조다.

### 부수 효과 (반드시 함께 검증)

같은 봉 튜플을 세 곳이 더 쓴다. 창이 2,880개로 늘면 **전부 값이 바뀐다.**

| 소비자 | 변화 | 위험 |
|---|---|---|
| `stop_slippage_from_bars` | q95 초과주행이 더 긴 표본에서 계산됨 | 손절 폭이 달라져 **사이징이 달라진다** |
| MACD 다이버전스 | 1,499 → 2,880봉에서 탐색 | 오래된 다이버전스가 새로 잡힐 수 있음 |
| 회귀(SMA 6/70/200) | 워밍업 여유 증가 | 낮음 |

**세 번째가 아니라 첫 번째가 위험하다.** 손절 폭 변화는 라이브에서 곧바로 금액이다. 수정 전후의 `stop_slippage_q95`를 같은 시점에 나란히 찍어 기록해야 한다.

### 검증

1. 단위: 페이지 경계에서 봉이 중복/누락되지 않음, 부족하면 빈 존
2. 재현: 오늘과 같은 봉으로 `at_all_time_high=False`일 때 **존이 0이 아님**
3. 프로덕션: 새 결정에서 `NO_MARKED_ZONE`이 사라짐 — **이것이 성공 판정 기준**

## 3. F3 — `at_all_time_high`를 봉에서 계산

### 원인 (확정)

`assembly.py:151` `at_observed_all_time_high: bool = False` — 기본값이고 아무도 설정하지 않는다. 원문은 `at_all_time_high(bars_5m)`라고 쓴다. **입력이 아니라 함수다.**

### 수정

`zones.py` 안에서 창의 봉으로부터 계산한다. 원문이 "관측된(observed)" 최고가라고 말하므로 **판정 근거는 우리가 보고 있는 창 그 자체**다.

정해야 할 것:

- **판정 기준.** 마지막 봉의 종가(또는 고가)가 창 전체의 최고가와 같거나 그에 준하는가. "그에 준하는" 여유를 얼마로 둘지는 원문에 없다 — **여유를 두면 그것은 추정이므로 파라미터로 분리하고 A0로 취급하지 않는다** (문서 5행).
- **순환 참조.** `at_all_time_high`가 창 길이를 정하는데 그 판정을 창에서 한다. 원문 의사코드도 같은 구조(`at_all_time_high(bars_5m)`)이므로 **긴 쪽(10일) 창으로 판정한 뒤 필요하면 3일로 좁히는** 순서가 원문에 어긋나지 않으면서 결정적이다.
- **`AssemblyInputs`의 필드 처리.** 계산으로 대체되면 이 필드는 남겨둘 이유가 없다. 남기면 "설정하면 계산을 이긴다"는 두 번째 진실이 생긴다.

### 검증

- 인위적 상승 창(마지막 봉이 최고가) → True, 하락 창 → False
- 프로덕션 현재 시점에서 **False로 나와야 한다** (BTC는 사상 최고가 구간이 아니다). True가 나오면 판정 기준이 틀린 것이다

## 4. F8 — 존 관측점이 원문과 다르다 (신규)

### 원인

원문 §10:

```python
pivots = collect(bars_5m, lookback_days,
                 kinds=['swing_high', 'swing_low', 'close', 'open'])
```

`zones.py:104`:

```python
observations = tuple(
    value for bar in selected for value in (bar.open, bar.high, bar.low, bar.close)
)
```

원문은 **스윙 고점·저점**(피벗)에 종가·시가를 더한다. 구현은 **모든 봉의 고가·저가**를 쓴다. 변수명조차 원문은 `pivots`다.

### 왜 결과가 달라지는가

모든 봉의 고·저를 쓰면 관측점이 크게 늘고 클러스터 밀도가 부풀어 오른다. 오늘 재현에서 실제로 나온 값:

```
77187.30-77381.20  touches=72
76989.90-77182.50  touches=39
```

`strength = min(touch_count, 5)`이므로 **강도는 즉시 포화된다.** 원문의 "고·저·고·저 반복 확인"(`touch_count < 3`)은 **구별되는 스윙의 반복**을 세라는 뜻인데, 지금은 지나간 모든 봉을 센다. 존이 더 넓고 더 많고 전부 강도 5로 나온다.

### 수정

관측점을 원문대로 바꾼다: 확정된 스윙 고점·저점 + 각 봉의 시가·종가. 피벗 산출은 이미 있다 — `assembly._divergence`가 `Pivot` 튜플을 만들고 `exhaustion`이 쓴다. **없는 것을 만드는 게 아니라 이미 있는 것을 연결하는 일이다.**

정해야 할 것:

- 피벗은 현재 MACD 정렬 후의 봉에서 산출된다. 존은 10일 창을 쓴다. **두 창이 다르면 피벗 인덱스가 어긋난다** — `_require_pivot_matches_bar`가 이미 그런 불일치를 잡도록 되어 있으니, 같은 창에서 산출하도록 배선해야 한다.
- 이 변경은 F2와 **함께** 해야 한다. 따로 하면 어느 쪽이 존 개수를 바꿨는지 구분할 수 없다.

### 검증

수정 전후로 같은 봉에 대해 존 개수·경계·touch 분포를 나란히 기록한다. **touch가 72에서 한 자리로 내려오고 strength가 포화를 벗어나는 것**이 기대 방향이다.

## 5. F1 — 양방향 평가

### 원인 (확정)

`risk_context.py:49` `side: Side = Side.BUY`, `run_shadow.py`가 넘기지 않음. 엔진은 방향을 **고르지 않는다** — `engine.py:125`에서 `risk_context.risk_request.side`를 받아 그 방향의 증거가 있는지 **검증만** 한다.

즉 방향은 리스크 컨텍스트를 만들기 전에 정해져야 한다.

### 원문이 정하는 순서

문서 1302행 요약: **"인트라데이에서는 가격이 극점을 갱신하는데 MACD가 반대로 가는 비대칭을 먼저 찾는다. 그 비대칭이 없으면 피보나치를 그리지도 않는다."**

방향은 **다이버전스에서 나온다.** 강세 다이버전스 → 롱, 약세 → 숏. 이것이 A0다.

### 선택지

| | 방식 | 장점 | 단점 |
|---|---|---|---|
| **A** | 소스에서 다이버전스를 먼저 계산해 방향을 정하고 그 방향으로 컨텍스트 구성 | 원문의 순서와 일치. 봉당 결정 1건 유지 | 어셈블리가 다이버전스를 다시 계산 (같은 입력·같은 함수이므로 값은 일치) |
| **B** | 양쪽 다 평가해 결정 2건 기록 | 거절 사유가 양방향으로 남아 증거가 풍부 | 봉당 1건 원칙이 깨짐. 승격 증거 집계가 달라짐 |
| **C** | 엔진이 방향을 고르도록 재설계 | 중복 없음 | 검증자였던 엔진을 선택자로 바꾸는 큰 변경. 회귀 위험 큼 |

**A를 권장한다.** 원문의 작업 순서와 같고, 봉당 1건 규약을 지키며, 중복 계산은 결정적 함수라 불일치가 원리적으로 불가능하다.

정해야 할 것:

- **양방향 다이버전스가 동시에 있을 때.** 엔진에 이미 `CONTRADICTORY_DIRECTION_EVIDENCE`가 있다. 소스에서 임의로 한쪽을 고르면 그 안전장치를 우회하게 된다. **모순이면 방향을 정하지 않고 그 사실을 기록하는 편이 안전하다.**
- **아무 다이버전스도 없을 때.** 원문은 "그리지도 않는다"이다. 지금처럼 REJECT를 기록하는 것과, 패스를 만들지 않는 것 중 어느 쪽이 맞는지는 **승격 증거 집계 방식에 달렸다** — REJECT도 세는지 확인 후 결정.

### 검증

- 인위적 약세 다이버전스 봉 → `side=SELL`인 결정이 생성됨
- 프로덕션: **SELL 결정이 하나라도 기록되면 성공.** 현재 17/17 BUY

## 6. F5 — 리스크 비율

**코드 문제가 아니다.** 바인딩된 정책 행(`01a05ab8-…`)의 데이터다.

| 항목 | 문서 | 라이브 |
|---|---|---|
| `normal_risk_fraction` | 0.0015 | 0.0025 |
| `a_risk_fraction` | 0.0025 | 0.0050 |

문서가 스스로 `source_status: IMPLEMENTATION_SAFETY_CANDIDATE_NOT_DAVID`라고 표기하므로 **원저자 위반이 아니다.** 그러나 명시된 유일한 수치와 어긋나고, 건당 위험이 1.67배다.

**이것은 운영자의 결정이며 내가 대신 정하지 않는다.** 선택지는 둘이다:

1. 정책을 문서 수치로 내린다 — 백오피스에서 새 정책 버전을 만들어 재바인딩
2. 현재 수치를 유지하고 **문서에 근거와 함께 반영**한다 — 근거 없이 코드만 남으면 다음 감사에서 같은 항목이 또 잡힌다

어느 쪽이든 **정책 버전을 새로 만들어야** 한다. 기존 행을 수정하면 이미 기록된 결정들이 소급해서 다른 정책을 가리키게 된다.

## 7. F6 — 보유 포지션 청산 규칙

원문 §21: `exit_before_blocking_big_trade: true`, 그리고 1302행 **"앞을 막는 대형 체결과는 싸우지 않고 나온다."**

현재 `BLOCKING_BIG_TRADE_AHEAD`는 **진입 차단으로만** 존재한다. 보유 포지션을 나오게 하는 경로가 없다.

섀도는 포지션을 열지 않으므로 지금은 무해하다. **페이퍼 승격 전까지 필요하다.**

이 항목은 진입 로직이 아니라 **보호·청산 경로**에 속하고, 그 경로는 이번 감사에서 검토하지 않았다. 착수 전에 별도 조사가 필요하다 — 현재 어떤 청산 트리거가 존재하는지, 어디에서 평가되는지.

## 9. 되돌리기

F2는 봉 창을 바꾸므로 **손절 폭과 사이징에 직접 영향**을 준다. 다음을 지킨다:

- 커밋을 F2+F3 / F8 / F1로 **분리한다.** 하나로 묶으면 사이징 변화가 어느 것 때문인지 사후에 구분할 수 없다
- 각 단계 전후의 `stop_slippage_q95`, 존 개수, 결정 분포를 기록에 남긴다
- 라이브 승격은 이 계획 전체가 끝나고 **섀도 2회·페이퍼 2회**(§11.7/§11.8)를 통과한 뒤다. 이 계획의 어떤 단계도 그 게이트를 앞당기지 않는다

## 10. 이 계획이 다루지 않는 것

- **F6의 구현 설계.** 청산 경로를 조사하지 않았다. 조사 후 별도 계획이 필요하다
- **§15.2 `telemetry_only` 항목들.** 감사에서 정상으로 확인했고 변경 대상이 아니다
- **승격 게이트 자체.** OOS 기대값 > 0.15R, PF ≥ 1.15, 셋업별 표본 ≥ 50 (문서 1295행) — 이 계획은 시스템이 그 표본을 **만들 수 있게** 하는 것까지다
