## F1 — 모든 평가가 영구적으로 BUY

### 근거

프로덕션 결정 17건의 `side` 분포:

```
17  BUY
 0  SELL
```

`src/autotrader/apps/trader/risk_context.py:49`

```python
def __init__(self, *, budget, policy, side: Side = Side.BUY) -> None:
```

`run_shadow.py`가 `BinanceRiskContexts(budget=..., policy=...)`로 생성하며 `side`를 넘기지 않는다. 기본값이 그대로 굳는다.

### 왜 문제인가

문서 §21 `prohibited` 목록(약 1030행)에 **`permanent_long_only`**가 명시되어 있다. 현재 구현은 그 금지 항목 자체다.

이것은 "숏 기회를 놓친다"보다 나쁘다. 하락 구조에서 나타나는 **약세 다이버전스와 고점 소진이 평가조차 되지 않는다.** 엔진은 매 패스 "롱이 성립하는가"만 묻고, 답이 아니오면 `DIRECTION_EVIDENCE_MISSING`(17건 중 11건)과 `REGULAR_DIVERGENCE_ABSENT`(11건)를 기록한다. 그 11건 중 숏이 성립하는 봉이 몇 개였는지는 **기록에 존재하지 않는다.** 평가하지 않았기 때문이다.

`Side.SELL` 경로는 코드에 존재한다 — `risk_context.py:79`가 숏의 구조적 기준선을 계산하고, `exhaustion.py`가 `bearish` 시퀀스를 만들며, `risk/v6.py`가 `INVALID_SHORT_STRUCTURAL_REFERENCE`를 검사한다. **연결만 한쪽이 비어 있다.**

### 유의

Binance USD-M 무기한 선물은 공매도가 가능하다. 현물 베뉴의 제약(`SPOT_VENUE_CANNOT_SHORT`)은 이 시장에 적용되지 않는다. 즉 이 제약은 베뉴가 아니라 배선에서 온다.

### 해결 (`b614ae5`)

방향을 정규 다이버전스에서 읽는다(§3: 비대칭을 **먼저** 찾는다). 답은 셋이며 호출자가 뭉개면 안 된다:

- **없음** → 셋업이 없다. 어느 쪽도 통과 못 하므로 패스는 계속 진행해 거절을 기록한다. `decision_count`가 승격 입력이고, 시스템이 보고 거절한 봉은 보고 있었다는 증거다
- **하나** → 그 방향으로 평가한다
- **양쪽** → 평가하지 않는다. 한쪽을 고르면 자기 다이버전스를 찾아 지지받는 것처럼 보이면서 `CONTRADICTORY_DIRECTION_EVIDENCE`를 우회한다

**커밋 전에 라이브에서 측정했다.** 합성 픽스처에서 "양쪽"이 흔하게 나와, 그대로라면 거의 모든 패스가 멈출 수 있었기 때문이다. 최근 120개 창에서:

```
없음 81   하나 39   양쪽 0
```

이전 코드가 롱을 120번 평가했을 자리에서, 39번이 시장이 가리키는 방향을 따른다.

페이퍼 소스(`market_data.py`)에도 같은 기본값이 있었고 함께 고쳤다 — 남겨두면 페이퍼 승격 시점에 금지 동작이 되살아난다.

프로덕션 봉 창은 Binance 클라인 상한 1,500개다. 5분봉 1,499개는:

### 왜 치명인가

`engine.py:156`

```python
final_grade = SetupGrade.REJECT if canonical_blockers else grade
```

**블로커가 하나라도 있으면 REJECT다.** 존이 비면 `NO_MARKED_ZONE`이 17/17로 붙고, 따라서 이 시스템은 **거래 가능한 결정을 낼 수 없다.** 섀도 2회 → 페이퍼 2회 → 라이브(§11.7/§11.8) 승격 경로 전체가 여기서 막힌다.

### 플래그를 켜서 해결하면 안 되는 이유

### 원문 재확인 결과 — 요구 자체는 옳다

이 항목에 처음 적었던 추정("존이 5분봉이 아니라 상위 시간대에서 오는 것 아닌가")은 **틀렸다.** 문서 §10이 의사코드로 직접 답한다:

```python
def build_zones(bars_5m, lookback_days=None):
    if lookback_days is None:
        lookback_days = 3 if at_all_time_high(bars_5m) else 10
```

입력은 **5분봉이 맞고**, 10일/3일도 **원문 그대로**다. 따라서 결함은 요구가 아니라 **그 요구만큼 데이터를 가져오지 않는 것**이다. `_REST_LIMIT = 1500`은 요청당 상한이며, `/fapi/v1/klines`는 `endTime`으로 역방향 페이징이 가능하다. 현재 `completed_bars`는 한 번만 호출한다.

수정 방안은 [수정 계획서](2026-09-02-remediation-plan.md) §2 참조.

## F4 — 소진 부재는 F2의 결과다

`EXHAUSTION_ABSENT`가 17/17로 나타나지만 독립 결함이 아니다.

`exhaustion.py`

```python
if len(history) < 2 or not _inside_zone(history[-1].price, zones):
    return None

def _inside_zone(price, facts) -> bool:
    return any(zone.lower_boundary <= price <= zone.upper_boundary
               for zone in facts.zones)
```

`facts.zones == ()`이면 `any(())`는 False다. 따라서 소진 시퀀스는 항상 None이다.

**영구 블로커 셋 중 둘이 하나의 뿌리에서 나온다:**

```
봉 창 5.2일 < 요구 10일
  └→ zones = ()
       ├→ NO_MARKED_ZONE            (17/17)
       └→ _inside_zone 항상 False
            └→ EXHAUSTION_ABSENT    (17/17)
                 └→ engine.py:156 → REJECT
```

F2를 고치면 둘 다 사라진다. 소진 로직 자체를 건드릴 이유는 현재 없다.

### 정정 — 예측이 빗나갔다 (2026-09-02, 결정 41건 시점)

F2가 해결되어 존이 19개 생성되는데도 **`EXHAUSTION_ABSENT`는 여전히 41/41이다.** "둘 다 사라진다"는 예측은 틀렸다.

메커니즘 자체는 맞았다 — 존이 비면 `_inside_zone`이 항상 False이므로 소진은 **구조적으로 불가능**했다. 그러나 존이 생겼다고 소진이 나타나는 것은 아니다.

**막는 지점은 다른 데 있었다.** `_sequence`는 "가격 갱신 + 거래량 감소"가 연속 피벗마다 이어지는 런을 요구하고, **그 런이 평가 시점에 살아 있어야** 한다. 라이브 봉에서 측정한 결과:

```
left right  pivots  %bars  best low run  run at end
   3     0    2631    59%             4           1
   3     3     832    19%             3           1
   5     5     551    12%             2           1
   8     8     369     8%             3           1
  12    12     248     6%             4           1
```

**어떤 피벗 폭에서도 끝에서의 런은 1이다.** 즉 F9가 지적한 피벗 관대함이 원인이 아니다. 런은 존재하지만(최장 4) 평가 순간에 살아 있는 경우가 드물다.

원저자의 규칙이 그렇다 — "새 저점이 나오는데 거래량이 계단처럼 줄어드는 소진을 **기다린다**". 시퀀스는 행동하는 순간에 현재형이어야 한다.

### 소진은 이제 발견 가능하다 (단, 측정에 한계 있음)

600개 평가 시점을 되짚어 계산한 결과 강세 161 · 약세 176 · 확정(런 3 이상) 85건이 나온다. **존 수정 전에는 전부 0이었다** — 시장이 무엇을 하든 답이 None이었다.

**이 수치를 그대로 믿으면 안 된다.** 프로브가 각 과거 시점에 **현재 창으로 만든 존**을 썼다. 실제 루프는 그 시점의 창으로 존을 만든다. 즉 미래를 참조했고 발견율은 과대평가다.

### 프로덕션에서 발견됨 (09-02 04:06:35)

관측을 이어간 결과 **첫 소진이 결정에 도달했다.**

```
09-02 04:06:35  HLIT  REJECT  BUY   matched=3 blockers=7
  blocked by : BLOCKING_BIG_TRADE_AHEAD, CALENDAR_BLOCKED,
               DIRECTION_EVIDENCE_MISSING, EXHAUSTION_UNCONFIRMED,
               REGULAR_DIVERGENCE_ABSENT, ROUNDED_QUANTITY_ZERO, SETUP_REJECTED
  matched    : blocking_big_trade_ahead, high_impact_news_risk,
               profile_value_confluence
```

**`EXHAUSTION_ABSENT`가 `EXHAUSTION_UNCONFIRMED`로 바뀌었다.** 시퀀스가 발견됐고, 피벗이 2개라 확정(3개 필요)에 미달했을 뿐이다.

존 수정 전에는 `_inside_zone`이 빈 튜플에 항상 False였으므로 **시장이 무엇을 하든 ABSENT**였다. 이제 경로가 프로덕션에서 살아 있음이 확인됐다. **F4의 메커니즘 주장은 옳았고, 예측한 시점만 틀렸다.**

**발견율은 되짚기 프로브가 크게 과대평가했다.** 존 보유 결정 31건 중 1건(3.2%)이고, 프로브의 56%와는 자릿수가 다르다. 미래 참조 결함을 결과와 함께 기록해둔 것이 옳았다.

같은 결정에 `CALENDAR_BLOCKED`와 `high_impact_news_risk`가 함께 붙어 있다. 04:06은 유럽 지표 시간대이고, §8 뉴스 필터가 의도대로 발동했다.

### 아직 확인되지 않은 것

`entry` · `stop` · `target`이 여전히 전부 None이다. 셋업이 REJECT면 레벨이 채워지지 않으므로 **사이징과 주문 형성 경로는 미검증**이다. 확정된 소진(피벗 3개)이 나오고 다른 블로커가 없는 봉이 필요하다.

즉 이 수치들은 **원저자의 것이 아니다.** 따라서 이것은 원저자 방법 위반이 아니라 **명시된 유일한 수치와의 불일치**다. 그럼에도 기록하는 이유는, 현재 시스템에 다른 근거가 없고 라이브 계정에서 건당 위험이 명시치의 1.67배로 잡히기 때문이다.

### 현재 완화되어 있음

`risk/v6.py:384`의 `_allowed()`가 `RESEARCH_SCORE_AUTHORITY == SCORE_ONLY`인 동안 상향 비율을 normal로 눌러둔다. 따라서 A등급의 0.0050은 실효적으로 0.0025다. **normal 자체의 0.0025는 눌리지 않는다.**

### halt 해결 (`954939e`)

`create_control`은 킬 스위치 레벨과 함께 **소유권·arming·만료를 덮어쓴다.** 운영자가 통제권을 가져올 때는 맞지만 전략이 스스로 멈출 때는 틀리다 — **조용히 리스를 갱신하는 halt는 계정을 원래 쥐고 있던 쪽에 되돌려준다.**

`trip_kill_switch`는 컬럼 하나만 쓰고, 바꾼 내용을 감사 로그에 남기고, 리스를 건드리지 않는다. **올리기만 한다** — 순서가 뒤바뀐 두 halt가 약한 쪽을 남기면 안 되고, 내리는 것은 백오피스에서 2차 비밀번호를 거친 운영자의 행위다.

**순서는 닫기 → halt다.** halt를 먼저 하면 **멈춘 계정 뒤에 포지션이 열린 채 남는데, 그것이 비상 청산이 벗어나려는 바로 그 상태**다.

실제 MySQL(`finance_auto_trading_test`) 통합 테스트 3건으로 확인: 레벨은 오르고 소유자·획득시각·만료는 그대로, 강한 halt 위의 약한 halt는 무효, 감사 로그에 이전·이후 레벨 기록.

### 손절 이동 (`226e39a`)

페이퍼 브로커가 `cancel`과 `replace` 둘 다 `ValueError`를 던지고 있었다(`e50e877`에서 구현). **손절 이동이 막혔던 건 판단이 아니라 브로커의 능력이었다.**

**두 액션을 한 경로로 처리한다.** 매니저는 한 패스 전 정보로 "활성화"인지 "이동"인지 판단하는데, 틀리면 **포지션 하나에 손절이 둘** 붙는다. 그 상태는 하위 어디에서도 잡히지 않는다 — **작동 중인 손절 둘은 둘 다 보호처럼 보인다.** 그래서 싱크가 매니저 말을 믿지 않고 실제로 무엇이 작동 중인지 직접 묻는다.

**취소 후 재배치가 아니라 교체다.** 그 사이의 순간이 아무것도 뒤에 없는 포지션이고, 그게 손절이 존재하는 이유다.

가격이 없으면 구조적 손절로 폴백하지 않고 **거절한다.** 폴백은 작동 중인 손절을 매니저가 요청한 적 없는 가격으로 옮기고, 게다가 성공한 것처럼 보인다.

### 가산 (`4e6b6c8`)

익스포저를 늘리므로 청산의 REDUCE가 아니라 **ENTRY 의도 · 신규 익스포저 권한 · 실제 리스크 예약**이다.

**순서가 설계다 — 손절 먼저, 그다음 가산.** 둘은 거래소에서 별개의 행위라 하나로 만들 수 없으므로, 중요한 건 절반만 실패했을 때 남는 상태다.

- **손절 먼저**: 가산이 실패하면 포지션은 원래 크기, 더 큰 포지션용 손절 뒤. 가중 BE는 원래 진입가와 현재가 사이이므로 기존 포지션에겐 **더 타이트하다** — 나쁜 체결이지 더 큰 위험이 아니다
- **가산 먼저였다면**: 커진 포지션이 **옛 손절 뒤에** 남는다. 승인된 어떤 것보다 큰 금액이 위험에 놓인다

그래서 손절 가격이 없는 가산은 이동 없이 수행하지 않고 **거절한다.** 이동은 가산의 부속이 아니라 **비용을 치르는 절반**이다.

예약은 새 한도가 아니라 **결과 최악 위험**이다. `_add_action`이 그 값이 이미 승인된 위험을 넘지 않을 때만 가산을 제안하므로, 기존 한도의 재진술이다.

### 배선 중 잡힌 결함 둘

**랏은 가산이 아니다.** `add_count = len(lots) - 1`로 시작했는데 랏은 **체결당** 하나다. 진입 주문 하나가 3번에 나눠 체결되면 가산 0인데 2로 센다. 도메인이 `add_count`를 0 또는 1로 제한하므로 **첫 부분체결에서 포지션이 관리 불가가 된다.** 주문 단위로 묶고 거래량 가중 평균하도록 고쳤다.

**명시적 0이 전량 청산이 됐다.** `action.quantity or position.remaining_quantity`에서 `Decimal(0)`은 falsy라 "미지정"으로 읽히고 포지션 전체를 닫는다 — 0이 요청한 것의 정반대. `is None`으로 고쳤다.

### 남은 조건

섀도는 포지션을 열지 않으므로 이 코드는 아직 한 번도 실행되지 않았다. **페이퍼 승격 전에 미구현 3종을 마저 만들어야 한다.**

## F9 — 존 강도가 항상 5로 포화한다 (F8 수정 후 신규)

### F8에 대한 내 예측이 틀렸다

F8 항목에 "관측점을 원문대로 바꾸면 touch가 72에서 한 자리로 내려온다"고 적었다. **측정이 이를 반증했다.**

2,880봉(10일) 라이브 데이터에서 원문 `kinds` 목록의 네 가지 해석을 모두 계산한 결과:

**어떤 해석도 touch를 한 자리로 내리지 못한다.** 포화의 원인은 관측점 집합이 아니었다.

### 실제 원인 두 가지 (이 절은 아래 「정리」가 반증했다)

> **이 절의 결론은 유지되지 않는다.** 아래 「정리」에서 방문 횟수로 다시 측정한 결과 그 정의로도 16/19가 포화했고, 포화는 계수 방식이 아니라 창의 길이에서 온다는 것이 확인됐다. 틀린 추론이 어떻게 진행됐는지 남기기 위해 지우지 않는다.

**첫째, 피벗 판정이 지나치게 관대하다.** `PivotConfig(left=3, right=0)`이 **2,880봉 중 1,686개(59%)를 스윙으로 표시한다.** 왼쪽 3봉만 보고 오른쪽을 보지 않으므로, 5분 암호화폐 데이터에서는 거의 모든 봉이 국소 극점이 된다. 이 설정은 다이버전스 탐지와 공유되므로 여기서만 바꿀 수 없다.

**둘째, 더 근본적으로 `touch_count`의 정의가 다르다.** 현재는 **가격 구간에 관측점이 떨어진 서로 다른 봉의 수**를 센다. 10일간 5분봉 2,880개 중 시장이 머문 가격대라면 수백 개가 걸린다. 원저자의 "고·저·고·저 반복"은 **사람이 차트에서 세는 몇 번의 되돌아옴**이지, 그 가격대를 지나간 모든 봉이 아니다.

`strength = min(touch_count, 5)`이므로 **모든 존이 최대 강도 5로 나온다.** 강도가 존을 구별하지 못한다.

### 왜 지금까지 안 보였나

존이 항상 비어 있었기 때문이다(F2). F2가 해결되면서 처음으로 관측 가능해졌다.

### 정리 (2026-09-02)

세 번째 가설까지 세웠고 **두 개를 측정이 죽였다.** 순서대로 기록한다.

**가설 1 — 관측점 집합이 원인이다(F8).** 틀렸다. 원문의 `kinds` 목록 네 가지 해석을 모두 계산했으나 상위 존 touch가 577 → 543으로 움직였을 뿐이다.

**가설 2 — `touch_count`는 봉이 아니라 방문(visit)이다.** 원저자의 주석 `고·저·고·저 반복`이 "가격이 나갔다 돌아온 횟수"를 뜻한다는 읽기다. 이 읽기라면 `min(touch_count, 5)`가 의미를 갖는다. **측정 결과 이것도 틀렸다:**

방문으로 세도 1~86회이고 **16/19가 여전히 상한에 붙는다.** 포화는 계수 방식이 아니라 **창의 길이에서 온다** — 10일치 5분봉에서 시장이 실제로 쓴 가격대는 어떻게 세도 5를 넘는다.

### 결론

**고치지 않았고, 고칠 근거도 없다.** 원문은 `cluster_by_density`를 정의하지 않고, 두 가지 자연스러운 읽기 모두 상한을 구제하지 못했다. 임계값이나 계수 규칙을 여기서 정하면 A0가 아니라 발명이며 문서 5행이 금지하는 혼합이다.

`min(touch_count, 5)`가 손으로 그린 사각형 몇 개를 보는 사람에게는 의미 있는 척도이고, 10일 창을 20개 구간으로 나누는 기계에게는 그렇지 않을 수 있다. **그 판단은 원문에 없다.**

### 남기는 조건

**`strength`를 점수에 반영하려는 순간 이 항목이 되살아난다.** 그때는 계수 규칙을 원문에서 먼저 확정해야 하고, 이 문서의 두 측정이 출발점이다.

## F10 — 세션 마감에 포지션이 닫히지 않는다

### 근거

`sessions.py`는 `must_be_flat`, `reduce_only`, `entry_cutoff_at`, `flat_at`을 전부 계산한다. 소비되는 방식은 **블로커 하나**뿐이다:

```python
if session_open and decision >= entry_cutoff:
    blockers.append("ENTRY_CUTOFF_REACHED")
if must_be_flat:
    blockers.append("FLAT_CUTOFF_REACHED")
```

블로커는 `engine.py:156`을 통해 **새 결정을 REJECT로** 만든다. 보유 포지션에는 아무 일도 일어나지 않는다.

### 원문이 요구하는 것

세션 마감 30분 전 진입 중단, **10분 전 평평**, 그리고 **오버나이트 금지**. 구현은 첫 번째만 한다. 이미 들고 있으면 **그대로 밤을 넘긴다.**

Binance USD-M은 24시간 열려 있으므로 이 세션 경계는 `binance_session.py`가 유동성 측정으로 정한 20:00 UTC다. 그 시각을 넘겨 포지션을 들고 가는 것은 원문이 금지한 것이고, 동시에 **그 경계를 정한 근거(얇은 유동성 구간을 포지션 없이 통과한다)를 무효로 만든다.**

### F6 배선이 이것을 덮지 않은 이유

`manage_v6_position`은 **세션 입력을 받지 않는다.** `V6PositionFacts`에 세션·시각 관련 필드가 없다. 따라서 F6에서 매니저를 배선해도 이 규칙은 여전히 실행되지 않는다.

### 해결 (`8377a2a`) — 매니저 안에 넣었다

두 선택지 중 **매니저**를 골랐다. **포지션에 무슨 일이 일어나는지는 한 곳이 정해야 한다** — 그것이 두 곳으로 갈리는 것이 이 감사가 찾아낸 결함 대부분의 원인이었다. `manage_v6_position`이 `must_be_flat`을 받고 `EXIT_FULL_SESSION_CLOSE`를 돌려준다.

**우선순위: 시장 판독 위, 망가진 손절 아래.** 마감 시각은 협상할 수 없다 — 테이프가 뭐라 하든 포지션은 나가므로, 기록되는 이유는 **협상 불가였던 쪽**이어야 한다. 다만 보호가 작동하지 않는 포지션이 더 급하고, 계정을 정지시키는 것은 그쪽뿐이다.

**시계를 읽을 수 없으면 닫지 않는다.** 사실 조립기에서 안전한 답이 자명하지 않은 유일한 부재였다. 나머지와 같은 방식으로 풀린다 — 포지션은 이미 가진 손절을 유지하고, 진입 경로가 세션 증거 없이는 독립적으로 진입을 거부하므로 **아무도 볼 수 없는 마감 뒤로 새 포지션이 쌓이지 않는다.**

## F11 — 코드 승격 게이트가 원저자 게이트를 대신할 수 없다

### 두 게이트

**코드** (`execution/promotion/models.py`) — 설계 문서 §11.7:

```python
REQUIRED_SESSIONS = 2   # 서로 다른 두 거래일
```

세션 하나의 조건은 그 날짜가 지났을 것, 결정이 1건 이상 있을 것, 차단 사건·미해소 대조·결과 불명 주문이 없을 것. `NO_ORDERS`는 PAPER에만 적용된다 — 섀도는 주문 없이 평가하므로.

**원저자 문서** §22.9와 1295행:

```yaml
Binance 트랙: 8주 섀도 후 유효성 확인 시 score_only 승격
승격 게이트: OOS 기대값 > 0.15R, PF ≥ 1.15, 셋업별 표본 ≥ 50,
             리페인트 테스트 통과, 자유 파라미터 ≤ 8
```

### 모순은 아니다. 그러나 대체도 아니다

코드의 `§11.7`은 전략 문서가 아니라 **설계 문서**를 가리킨다. 두 문서가 서로 다른 것을 규정하므로 충돌이 아니다.

문제는 읽히는 방식이다. **"섀도 2회 완료"가 승격 준비 완료로 읽히면 안 된다.** 코드 게이트는 *운영이 돌아가는가*를 묻고, 원저자 게이트는 *전략이 돈을 버는가*를 묻는다. 전자를 통과해도 후자에 대해 아무것도 말하지 않는다.

### 지금은 후자를 계산할 수 없다

결정 54건이 전부 REJECT이고 진입이 0건이다. **OOS 기대값·PF·셋업별 표본은 재료 자체가 없다.** 리페인트 테스트와 자유 파라미터 수도 마찬가지로 아직 아무도 확인하지 않았다.

### 현재 준비 상태 (2026-09-02)

```
  utc date  decisions  evidence
2026-09-01         11  decisions=11 orders=0 incidents=0 recon=0 unknown=0   청구 가능
2026-09-02         43  decisions=43 ...                                       오늘, SESSION_NOT_OVER
```

09-01은 코드 게이트의 세션 조건을 충족한다. 09-02는 UTC 자정 이후 충족된다.

### 결정 — `ready`는 세션 수로 도달할 수 없다

`PromotionState.ready`의 docstring이 스스로 문제를 말하고 있었다: **"This is what LIVE activation asks."** 그런데 세션 수만으로 계산됐다. 하루에 결정 하나씩 이틀이면 `ready`가 True가 되고, 그것이 라이브 활성화가 묻는 값이었다.

**결정**: `ready`를 둘로 나눈다.

- `sessions_satisfied` — 운영 선행조건. **시스템이 돌았고 기록했다**는 것만 말한다
- `strategy_gate` — 계산이 아니라 **기록된 판단**. `NOT_EVALUATED` / `PASSED` / `FAILED`
- `ready` — 둘 다 필요

**세션을 아무리 세도 `PASSED`에 도달하지 못한다.** `promotion_state`는 세션을 읽고, 세션은 지켜본 하루이며, 그것이 몇 개든 전략에 대한 판단이 아니다.

현재 시스템에서 `PASSED`를 만들 수 있는 경로는 없다. **그래서 라이브는 오늘 도달 불가능하고, 그것이 옳은 답이다** — 지금까지 모든 결정이 진입 없는 REJECT다.

### 왜 원저자 수치를 코드에 넣지 않았나

그것이 대안이었고 **자기 조건에서 실패한다.** 진입이 0이면 기대값이 정의되지 않으므로 게이트가 영구히 만족 불가가 되고, **통과할 수 없는 게이트는 결국 누군가 지운다.** 판단을 기록하게 만드는 편이 정직하다 — 코드는 원저자 게이트를 계산할 수 없지만, 누군가 그것을 평가했다고 기록하기 전까지 "준비됨"이라고 말하지 않을 수는 있다.

미평가 항목 5종을 `STRATEGY_GATE_CRITERIA`로 명명했다. 화면이 **무엇이 평가되지 않았는지 말할 수 있어야** 읽는 사람이 "아무것도 없다"고 넘겨짚지 않는다.

### 남은 조건

- `PASSED`를 기록하는 경로(운영자 증언)는 만들지 않았다. **만들기 전에는 라이브가 열리지 않으며, 그것이 현재 옳은 상태다**
- 진입이 발생해야 OOS 기대값·PF·표본을 계산할 재료가 생긴다
- 리페인트 테스트와 자유 파라미터 계수는 별도 작업이며 이 감사에서 다루지 않았다

- **F1의 숏 평가** — 약세 다이버전스가 발생하지 않았다 (전 기간 73건 중 방향이 증거로 뒷받침된 것은 5건, 전부 강세)
- **F6의 행동 9종 전부** — 섀도는 포지션을 열지 않는다
- **사이징과 주문 형성** — 승인된 셋업이 한 번도 없었다
- **F5의 새 위험 비율** — 사이징이 실행되지 않았으므로 금액에 반영된 적이 없다

## 방법론 메모

F7과 F3은 **런타임 증거로만** 발견됐다 — 코드를 읽어서는 "필드에 기본값이 있다"까지만 보이고, 그 기본값이 매 패스 결과를 뒤집는다는 사실은 프로덕션 결정의 블로커 분포를 세어야 드러난다.

권장 상시 점검: **모든 결정에서 나타나는 블로커, 그리고 한 번도 나타나지 않는 증거 키.** 둘 다 "한쪽만 연결된" 결함의 지문이다.

이 감사에서 그 점검이 실제로 잡아낸 것: F7(캘린더), F3(ATH 플래그), F6(포지션 관리 전체), F10(세션 마감). 반대로 **읽기만 해서는** 넷 다 "필드에 기본값이 있다" 또는 "함수가 존재한다"까지만 보인다.

두 번째 메모: **예측을 기록하면 반증된다.** F4는 예측 시점이 틀렸고, F8은 예측한 효과가 나오지 않았고, F9는 가설 두 개가 측정에 죽었고, 6시간 세션에서는 "창 확대가 다이버전스를 죽였다"는 의심이 두 깊이 재생으로 반증됐다. 셋 다 그대로 남겨뒀다 — 무엇을 근거로 무엇을 예상했는지가 남아야 다음 사람이 같은 추론을 반복하지 않는다.
